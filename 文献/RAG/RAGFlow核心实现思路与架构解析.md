# RAGFlow 核心实现思路与架构解析

本文依据本地 `RAGFLow/ragflow` 源码整理，重点分析 Python 文档处理、检索与问答链路，不展开部署、任务调度和存储运维。整理日期：2026-09-08。

本文解释的是源码中的设计机制及其可能带来的效果收益，未运行对比评测；功能是否生效取决于解析方式、模型和配置，不能把所有增强能力视为默认执行步骤。

## 一、核心思想与整体架构

RAGFlow 的核心是逐步提高证据质量：先正确理解原始文档，再建立多种检索表示，通过混合检索和重排序寻找相关证据，最后把完整且受长度约束的材料交给大模型。

系统分为两条主要链路：

```text
文档入库链路
PDF / Word / 表格等
    ↓
解析文字、版面、表格和位置
    ↓
按内容结构、分隔规则和长度切块
    ↓
生成分词、向量，以及可选关键词和问题
    ↓
建立全文索引与向量索引
    └─ 可选增强：RAPTOR 摘要层、知识图谱

在线问答链路
用户问题 + 对话历史
    ↓
可选：多轮问题补全、跨语言处理、关键词扩展
    ↓
全文检索 + 向量检索
    ↓
重排序、阈值过滤、选择相关片段
    ↓
可选目录增强；存在父子块关系时恢复父块
    ↓
按上下文预算组织证据
    ↓
大模型生成答案、处理引用
```

一个关键设计是：**用于匹配问题的内容，可以不同于最终交给模型阅读的内容。** 小块、关键词和生成的问题有助于定位资料；父块、原文和图表上下文有助于理解与回答。

## 二、关键步骤 1：把原始文档解析正确

### 2.1 为什么不能只提取纯文本

PDF 的字符存储顺序不一定等于阅读顺序。双栏排版、页眉页脚、跨行段落和表格，都可能导致文本顺序或关系丢失。错误一旦进入知识库，后续检索和生成很难恢复原意。

例如，表格中“产品 A、标准版 100、企业版 300”如果被提取为“A 100 300”，价格与版本之间的关系就不再明确。

### 2.2 DeepDOC 的实现过程

1. 获取页面图像与文本字符，结合 OCR 获取文字。
2. 识别版面区域，区分正文、标题、表格和图片等内容。
3. 使用表格结构识别恢复行、列、表头及跨格关系。
4. 合并文本行与段落，处理阅读顺序和页面噪声。
5. 输出文本、图表及页码、坐标等来源信息。

文本连接不是仅按换行符处理：源码结合规则与 XGBoost 模型判断上下文本是否应拼接。表格则有独立的结构识别过程。

### 2.3 为什么有助于提升效果

这一步减少信息在检索前就发生的损坏，尤其适用于扫描件、复杂版式和表格密集文档。具体效果仍受原始扫描质量、版式和解析模型影响。DeepDOC 是可选解析路径之一，不能将其处理方式泛化为所有文件路径。

源码入口：`RAGFLow/ragflow/deepdoc/parser/pdf_parser.py`，重点看 `__call__`、`_layouts_rec`、`_table_transformer_job`、`_text_merge`、`_concat_downward`。

## 三、关键步骤 2：切块兼顾检索精度与上下文完整性

### 3.1 通用切块方式

通用切块逻辑利用格式解析结果与分隔符拆分内容，再按 token 数量合并。不同格式具有对应处理，还支持重叠、图表上下文和子块分隔配置。

因此，它是文档结构、规则和长度限制的组合，不能概括为全部自动语义切分，也不能概括为固定字数切分。

### 3.2 父子块机制

```text
父块：完整的退款规则
  ├─ 子块：申请期限
  ├─ 子块：申请材料
  └─ 子块：特殊情况及例外
```

用户问“超过期限还能退吗”，先检索较小的子块；命中后通过 `mom_id` 找回父块，让模型同时看到条件和例外。多个子块命中同一父块时，可以归并处理；父块缺失时保留子块作为回退。

### 3.3 为什么有助于提升效果

- 小块主题更集中，减少向量表示和匹配时的无关内容干扰。
- 父块恢复补充完整条件，降低断章取义的概率。
- 图表上下文帮助解释表格或图片中的内容。

父块扩大后也会增加上下文用量，需要控制粒度。未建立父子关系时，不会凭空获得父块恢复能力。

源码入口：`RAGFLow/ragflow/rag/app/naive.py` 的 `chunk`；`RAGFLow/ragflow/rag/nlp/search.py` 的 `retrieval_by_children`。

## 四、关键步骤 3：为片段建立多种检索表示

一个片段不只是“正文 + 向量”，还可以拥有以下信息：

| 表示 | 作用 |
|---|---|
| 正文分词与细粒度分词 | 支持词语与局部词项匹配 |
| 文件名相关字段 | 提供文档主题线索 |
| 重要关键词，可选生成 | 突出关键概念 |
| 片段可回答的问题，可选生成 | 缩短用户问题与文档表达之间的距离 |
| 向量 | 匹配措辞不同但语义接近的内容 |
| 文档、页码、坐标、父块关系 | 限定范围、恢复上下文、追溯来源 |

例如，原文是“设备连续运行八小时后，应停机检查冷却系统”，可以生成“设备运行多久需要检查”“应检查哪个系统”等问题，增加与用户提问接近的表达。

### 4.1 本地向量生成的具体逻辑

在 `embedding` 函数中：

1. 如果片段存在 `question_kwd`，优先编码生成的问题；否则编码正文。
2. 编码文件名，将其向量按权重融入片段向量。
3. 将最终向量保存到与维度对应的字段中。

该函数默认文件名权重为 0.1，可近似表示为：

```text
片段向量 = 0.1 × 文件名向量
         + 0.9 × 正文或生成问题的向量
```

这意味着生成问题在该路径中可能替代正文作为向量化输入，并非必然额外保存一份问题向量。原文仍用于其他检索字段及回答上下文。

### 4.2 收益与边界

多种表示可以覆盖精确术语和自然语言提问的差异。但生成的问题可能遗漏细节，文件名也可能缺乏语义，因此不能认为增加这些表示必然提高所有问题的召回率。

源码入口：`RAGFLow/ragflow/rag/svr/task_executor.py` 的自动关键词、自动问题处理及 `embedding`；`RAGFLow/ragflow/rag/nlp/query.py` 的 `FulltextQueryer`。

## 五、关键步骤 4：问题预处理与混合召回

### 5.1 把问题变成适合检索的表达

普通问答链路支持按配置执行：

- 多轮问题补全：结合历史对话明确“它”“那个方案”等指代。
- 跨语言处理：帮助问题匹配其他语言资料。
- 关键词扩展：增加查询中的关键概念。

这些处理是可选步骤。改写应尽量保留原始意图，避免改变限制条件。

### 5.2 全文检索与向量检索互补

| 问题类型 | 更需要的能力 |
|---|---|
| “ZX-240 的额定功率是多少？” | 型号等精确词项匹配 |
| “设备太热了怎么办？” | 匹配“过热保护”“散热异常”等语义 |

全文查询构造还包含分词、词项权重、同义词扩展和字段权重。关键词、生成的问题、文件名相关字段和正文并非同等权重。

向量检索将问题编码为查询向量，通过相似度寻找候选片段。两类信号结合，可以同时照顾精确名称与语义近似。

具体融合与评分实现会随索引后端和配置变化，不应把某一组固定权重当成所有路径的统一公式。

源码入口：`RAGFLow/ragflow/rag/nlp/query.py` 的 `question`；`RAGFLow/ragflow/rag/nlp/search.py` 的 `search`、`get_vector`、`retrieval`。

## 六、关键步骤 5：重排序与证据筛选

混合召回得到候选后，还需要判断哪些内容真正有助于回答当前问题。

- 未配置独立 reranker 时，组合词项匹配、向量相似度等信号排序。
- 配置 reranker 时，将问题与候选文本交给重排序模型评分，再与词项等信号融合。
- 排序后，根据相关配置进行阈值过滤与结果选择。

需要区分三个数量：

```text
检索候选池大小
    ↓
参与重排序的候选数量
    ↓
最终进入上下文的片段数量
```

先给召回留出空间，再精细筛选，可以减少“主题相近但答非所问”的材料。重排序无法补救候选池之外的遗漏，因此应先确认正确证据能被召回。

源码入口：`RAGFLow/ragflow/rag/nlp/search.py` 的 `rerank`、`rerank_with_knn`、`rerank_by_model`、`retrieval`。

## 七、关键步骤 6：组织上下文、生成答案与引用

检索结果不会直接无上限地交给模型，普通问答主链路还包括：

1. 按配置执行目录增强。
2. 对存在父子关系的命中片段恢复父块。
3. 按配置加入图谱等补充结果。
4. 根据 token 预算组织知识片段并装入提示词。
5. 将问题、对话历史和证据交给大模型生成答案。
6. 要求生成引用，并规范引用格式。

在满足对应空上下文条件且配置了空结果回复时，系统可以返回预设回复。这并不意味着默认具备可靠的“证据不足判断”或绝对拒答能力。

引用能够增强可核验性，但不等同于事实验证。源码还支持在模型未输出引用时，用答案片段与检索材料的相似度补配引用；相似度不能证明来源严格支持每个结论。

源码入口：`RAGFLow/ragflow/api/db/services/dialog_service.py` 的 `async_chat`；`RAGFLow/ragflow/rag/nlp/search.py` 的 `insert_citations`。

## 八、可选高级增强

### 8.1 RAPTOR：增加概括层级的证据

基本过程是：片段分组 → 生成摘要 → 摘要向量化 → 继续分组与摘要，形成多层摘要表示，并将摘要作为可检索内容入库。

底层片段用于细节问题，上层摘要增加回答全局概括问题的机会。例如“整篇报告的主要风险是什么”通常需要跨越多个原始片段。

本地代码的一个重要特点是：利用相邻片段向量的余弦相似度进行连续分组，再递归生成摘要，不能直接套用其他版本或论文中的聚类实现。构建摘要层也不等于每次查询都必须逐层遍历树。

边界：摘要可能遗漏细节或引入偏差，具体数值、限制条件仍应回看原文。

源码入口：`RAGFLow/ragflow/rag/advanced_rag/knowlege_compile/raptor.py`；`rag/svr/task_executor.py` 的 `run_raptor_for_kb`。

### 8.2 GraphRAG：补充实体关系结构

基本过程是：抽取实体和关系 → 构建与合并子图 → 可选实体消歧和社区报告 → 查询时检索图谱相关内容作为补充证据。

它适合跨片段、跨文档的关系问题，例如查找同一主体涉及的项目和相关事件。普通局部事实问题未必需要图谱。

边界：实体抽取、同名消歧和关系判断错误会传播到后续回答；图谱不能取代原始来源。

源码入口：`RAGFLow/ragflow/rag/graphrag/general/index.py` 的 `run_graphrag_for_kb`。

### 8.3 Agentic RAG：根据证据缺口继续检索

这份源码还有独立的 Agentic RAG 能力层，将问题整理、文档范围选择、关键词分析、知识库或其他来源检索、证据充分性判断和后续问题生成组织为多步过程。

它适合一次查询无法找齐材料的问题，例如比较两个方案并解释差异原因：先找双方资料，再针对缺失指标继续查询。

边界：更多步骤也会增加延迟和错误传播机会；模型判断“证据充分”不等于已完成严格验证。它与普通单次检索问答链路应区分理解。

源码入口：`RAGFLow/ragflow/rag/advanced_rag/agentic_rag.py`、`agentic_rag_graph.py`。

## 九、为什么这些设计有助于效果提升

| 常见失败 | RAGFlow 中对应的机制 | 主要作用 |
|---|---|---|
| PDF 阅读顺序或表格关系错误 | 版面、OCR、表格结构识别与文本合并 | 减少原始信息损坏 |
| 片段过长导致主题分散 | 按结构和长度切块 | 提高局部匹配精度 |
| 片段过短导致条件缺失 | 父子块与上下文恢复 | 提高证据完整性 |
| 用户问题与原文措辞不同 | 向量、生成问题、同义词等 | 扩展表达覆盖范围 |
| 型号或术语匹配不准 | 全文检索与字段权重 | 保留精确词项信号 |
| 召回结果相关但不回答问题 | 重排序与过滤 | 提升上下文相关性 |
| 细节检索难以覆盖全文 | RAPTOR 摘要层 | 增加概括级证据 |
| 关系散落在多份材料中 | GraphRAG | 补充实体关系线索 |
| 一次检索证据不齐 | Agentic RAG | 支持有针对性的后续检索 |
| 答案难以核验 | 来源位置与引用 | 支持人工追溯 |

这些收益可以相互配合，但不是简单叠加。解析质量、文档类型、问题分布、模型能力和参数都会影响最终效果。

## 十、借鉴实现时的优先顺序

1. **先验证文档解析。** 检查原文顺序、表格对应关系、页码和段落是否正确。
2. **再调整切块。** 检查真实问题需要的条件是否被切散，必要时建立父子块。
3. **建立混合检索。** 同时覆盖精确术语与语义表达，确认正确证据能够进入候选池。
4. **加入重排序。** 在召回足够的前提下提升最终片段的相关性。
5. **控制证据组织。** 保留必要上下文，限制噪声与长度，并支持来源追溯。
6. **按问题类型增加高级能力。** 概括问题考虑摘要层，关系问题考虑图谱，多步问题考虑迭代检索。

可以使用一组包含“问题、正确来源、必要条件、期望答案”的真实样例逐步检查：原文是否解析正确 → 正确块是否召回 → 是否排入最终上下文 → 上下文是否完整 → 答案是否受证据支持。这样能定位问题发生在哪一层，避免仅靠更换大模型或叠加高级功能尝试修复。
