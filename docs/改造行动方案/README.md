# 多源异构数据多智能体系统改造行动方案

## 1. 使用说明

本方案将[目标架构](../系统架构设计.md)拆成八个可以独立验收的阶段。每个阶段包含“设计文档”和“行动文档”：先确定协议与边界，再按任务编号实施，完成出口验收后进入下一阶段。

本轮交付的是实施文档，尚未修改运行代码。文中新增目录、接口、命令和测试都是待实现约定；不能将其视为已经可用的功能。代码核查日期：2026-09-07。

默认采用 Python 模块化单体、本地资产仓、SQLite 起步，保持 CLI 可运行；随后增加工作进程和 API。无需先引入微服务、消息中间件或特定 Agent 框架。模型通过网关接入，业务协议不绑定供应商。

## 2. 改造主线与阶段入口

先完成“源数据 → 语义观测 → 可追溯分析”的纵向切片，再扩展结构适配和协作。优先使用合成 XX 量表及已有导出格式，避免一开始同时处理全部模态。

| 阶段 | 核心结果 | 设计 | 行动 | 前置阶段 |
|---|---|---|---|---|
| 01 | 基线、公共协议、最小证据存储与新入口 | [设计](01-基础协议/设计.md) | [行动](01-基础协议/行动.md) | 无 |
| 02 | 程序化适配旧 JSON、宽表、长表及嵌套结构 | [设计](02-确定性适配/设计.md) | [行动](02-确定性适配/行动.md) | 01 |
| 03 | 语义映射候选、验证、补充说明及复用 | [设计](03-语义理解/设计.md) | [行动](03-语义理解/行动.md) | 02 |
| 04 | 专业 Agent 基于语义证据分析 | [设计](04-专业能力/设计.md) | [行动](04-专业能力/行动.md) | 02；映射自动化依赖 03 |
| 05 | 按目标规划、依赖调度与模型预算 | [设计](05-任务调度/设计.md) | [行动](05-任务调度/行动.md) | 04 |

## 3. 从代码到模块的迁移关系

以下定位来自对代码的阅读；复用前仍需通过对应阶段测试。

| 代码入口 | 改造内容 | 承接模块 | 阶段 |

| case_memory.py | 共享可变字典改为运行上下文和仓储引用 | domain/、storage/ | 01 |
| agents/data_quality_agent.py | 深拷贝和固定表单检查拆为映射验证、目标相关质量检查 | ingestion/、mapping/、capabilities/ | 02—04 |
| rwe_data_tools/export_patient_agent_json.py | 导出作为一种来源，保留来源定位；不让下游依赖中文字段 | ingestion/legacy_rwe.py | 02 |
| agents/cognitive_agent.py、functional_agent.py | 字段解释移入映射；计算和角色分离 | registries/、capabilities/、agents/ | 04 |
| agents/longitudinal_agent.py | 显式排序、可比性分组、数据不足状态 | capabilities/longitudinal.py | 04 |
| agents/biomarker_agent.py | 明确标本、平台、单位和解释条件 | capabilities/laboratory.py | 04 |
| agents/base_agent.py、llm_client.py | Agent 返回类型化产物；LLM 调用集中预算和验证 | agents/base.py、infrastructure/model_gateway.py | 04、05 |
| orchestrator.py | 固定列表改为经验证的任务依赖图 | orchestration/ | 05 |
| agents/synthesis_agent.py | 形成具体发现，保留反对证据及依赖 | collaboration/ | 06 |
| explainable_report.py 及两类报告脚本 | 提前生成证据标识；各格式渲染同一报告快照 | reporting/ | 01、06 |

认知、功能等角色可在目标实现中合并为量表专业 Agent；“认知/功能”作为测量领域保留，不要求维持原来的 Agent 数量。

## 4. 推荐目录布局

以下路径相对仓库根目录：

```text
src/multi_agent/
  domain/          # 协议与不变量，不依赖 LLM 或文件解析器
  application/     # 用例服务、CLI、API
  ingestion/       # 资产登记、解析、来源适配、画像
  mapping/         # 声明式算子、候选生成与验证
  registries/      # 量表定义、映射、能力注册
  storage/         # 仓储、快照、依赖关系、事务
  capabilities/    # 确定性计算与模型工具
  agents/          # 使用能力和证据的专业角色
  orchestration/   # 规划、状态机、调度与预算
  collaboration/   # 综合、质询、复核选择
  knowledge/       # 文档、检索、候选规则
  reporting/       # 发布检查与格式渲染
  infrastructure/  # 模型网关、进程执行、日志
configs/
  instruments/ mappings/ capabilities/
tests/
  unit/ integration/ acceptance/ fixtures/
evaluation/        # 脱敏评估材料、运行清单与结果
```

包名、协议名一旦阶段 01 确认，就贯穿后续实现。原根目录 agents/ 与新包内 agents/ 并存期间使用绝对包导入，避免同名模块遮蔽。已有 test/ 是另一套实验代码，新验证统一放 tests/。

## 5. 里程碑与范围管理

- M1（01—02）：不调用 LLM，三种以上结构进入同一语义模型，观测能回到源位置。
- M2（03—04）：陌生字段可以产生受验证的映射候选；缺说明时等待；专业分析不读源字段。
- M3（05—06）：由具体证据问题触发复核，报告体现修订和未解决项。这是核心协作闭环。
- M4（07—08）：多模态接入、恢复与版本管理完成，通过端到端验收后切换入口。

M3 可作为核心功能演示版本；不能把它描述为完整实现全部目标架构。复杂 OCR、新影像模型训练、跨量表校准不自动纳入本轮；遇到这些需求登记为能力缺口。阶段 07 必须实现能力不足的正确处理。

工作拆分粒度建议为一个行为变化一个提交或 PR。每个阶段先合协议，再合实现，最后合验收材料。工期需依据阶段 01 的依赖盘点和数据可得性排期，不以固定周数代替出口条件。

## 6. 通用验收与回退原则

1. 所有阶段使用[验收与场景清单](验收与场景清单.md)，记录实际命令、环境、输入版本、结果和未解决问题。
2. 正确性以独立标注和业务定义为依据。旧系统输出只是对照，已知错误不得成为金标准。
3. 新旧结果分目录、分运行标识保存；差异按预期纠错、未实现能力、缺陷、无法判断分类。
4. 迁移采用新入口和兼容适配器逐步替换。运行一旦开始绑定一个实现版本，不能在中途混用新旧证据。
5. 默认入口切换前保留旧命令与数据。切换失败可退回旧入口；对数据修订和已发布报告不做破坏性覆盖。
6. 真实模型、数据库和 GPU 验证单独记录；合成样本与 mock 通过不等于这些能力已验证。
7. 没有新增证据、映射或规则时，同一质询不得无限重试；网络重试与语义复核分别计量。

## 7. 建议从哪里开始

首先执行 01-A1：盘点依赖与可复现输入，制作一个有明确计分说明的合成 XX 量表案例。随后实现 SourceAsset、Observation、Evidence 和 SQLite 仓储，用来源定位检查完成第一条纵向链路。阶段 02 再让同一案例以不同结构输入。

不要在这一步重写全部 Agent。先使输入与证据协议稳定，后续角色、调度、复核才能围绕同一套对象协作。
