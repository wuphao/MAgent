# RAG 知识服务实施行动方案

日期：2026-09-08。状态：技术实施方案草案，尚未开始代码改造。

## 1. 目标与已确认条件

在现有 `src/multi_agent/knowledge` 与 `KnowledgeAgent` 上实现可追溯的 RAG 知识服务，为各业务智能体提供相关原文、真实版本、适用条件、冲突信息和规则候选。

- 向量模型固定为本地 Ollama 的 `qwen3-embedding:0.6b`。
- 保持患者观测、参考知识、规则候选和已激活规则的语义边界。
- 参考 RAGFlow 的解析、切块、混合召回、上下文恢复等思路，不整体搬入其应用和存储体系。
- 本次交付为行动方案；模型下载、依赖安装、索引构建和代码修改均列为后续动作。
- 默认第一轮面向小型本地知识库，以 Markdown、TXT、机器可读 PDF 为输入；扫描 PDF/OCR、复杂表格解析列入第二轮，遇到不支持的输入明确报告。

### 1.1 当前状态核查

| 项目 | 实际情况 |
|---|---|
| 文档加载 | `KnowledgeDocumentLoader` 读取 Markdown，按空行切块 |
| 来源 | 有文档 ID、版本字段、内容哈希和段落定位 |
| 版本接入 | `KnowledgeAgent` 目前统一传入版本 `1`，需要读取真实文档清单 |
| 检索 | `ExactRetriever` 按空格等拆分查询，以子串命中数排序；不是 BM25 |
| 索引 | `KnowledgeIndex` 为内存片段列表，每次 Agent 执行重新加载 |
| 返回结构 | `RetrievalHit.score` 为整数，需适配连续分值并保留各路分数 |
| 规则候选 | 包含 `total/总分` 即生成候选，尚不能可靠提取适用条件 |
| 向量与重排 | 主实现未接入 |
| Ollama | 本机 `http://localhost:11434/api/tags` 可访问，执行文件为 `D:\ollama\ollama.exe` |
| 指定模型 | 本次返回的模型列表未包含 `qwen3-embedding:0.6b`，未验证向量调用 |

依据：`src/multi_agent/knowledge/{documents,index,retrieval,rules}.py`、`src/multi_agent/agents/knowledge.py`、阶段 07 设计与现有集成测试。

## 2. 目标流程与实现选择

```text
入库：文档清单 → 解析与来源定位 → 父子切块
                  → 中文词法表示 + Ollama 向量 → 版本化索引

查询：业务问题 + 项目/版本/适用上下文
       → 明确条件过滤 → BM25 与向量双路召回 → RRF 融合
       → 可选独立重排序 → 父块恢复与去重 → 上下文预算控制
       → KnowledgeAgent 返回证据与候选
       → 业务智能体分析 / 报告引用
       → 涉及规则变更时经过注册激活
```

### 2.1 第一轮默认选择

- **向量接口：**Ollama `POST /api/embed`，封装为 `embed_documents` 和 `embed_query`。
- **向量存储：**复用 SQLite 存放片段、索引版本和向量；以 NumPy 对符合过滤条件的向量进行归一化余弦精确检索。第一轮不引入独立向量数据库。以真实规模测量时间和内存，达到项目预算后再替换为 ANN 后端。
- **词法检索：**中文分词、英文/数字/型号规范化，加 BM25；术语字典独立配置。实现时可用 `jieba`、`rank-bm25`，先验证版本和分词样例，再锁定依赖。索引按版本加载一次，避免每个问题重建。
- **融合：**采用 RRF，以排名融合不同检索分数，避免直接相加 BM25 和余弦值。初始 `k=60`，作为待评测参数。
- **排序：**第一轮只有混合融合排序，不能宣称已具备模型重排序。第二轮为独立 reranker 做验证和接入。
- **生成：**沿用现有业务智能体和报告模型接口，不由 embedding 模型生成回答。通用对话页面不是本次必要交付。
- **索引切换：**新索引验证后切换活动版本；查询始终绑定同一索引快照。原文版本与历史引用不随索引重建删除。

## 3. 第 0 步：冻结评测样例与当前基线

目标：先确定如何证明改进，避免只凭回答流畅程度判断 RAG 效果。

行动：

1. 盘点 `configs/knowledge`，选择实际使用的字典、手册和说明，记录真实来源与版本。
2. 建立至少 40 条初始问题，覆盖中文自然提问、英文缩写、编号、版本差异、表格、条件例外、无答案、冲突及跨段落问题；可以一题覆盖多个标签。
3. 每题标注正确文档版本、原文证据区间、必需条件、排除版本和是否可回答。黄金证据按原文区间标注，再映射 chunk，避免切块变化使评测失效。
4. 按来源或问题族划分调参集与冻结验收集，减少近重复泄漏；小样本报告实际命中数和分母。
5. 运行当前检索器保存基线。现有单个关键词命中测试继续保留，但不能代替检索质量评测。

产物：`evaluation/rag/dataset.jsonl`、`baseline.md`、来源清单及问题标签统计。

完成条件：每个可回答问题有可核验原文；无答案样例确定知识库确实不含答案；尚未核对的业务答案标记待核对，不纳入正式指标。

## 4. 第 1 步：接入本地 Ollama 向量模型

行动：

1. 检查 Ollama 版本、服务地址和模型列表。
2. 执行 `ollama pull qwen3-embedding:0.6b`，记录实际模型 digest；需要权限时按运行环境审批机制执行。
3. 新增 `knowledge/embeddings.py`，提供批量文档向量化和单条查询向量化。
4. 调用协议如下：

```json
{
  "model": "qwen3-embedding:0.6b",
  "input": ["需要编码的文本"],
  "truncate": false
}
```

接口地址为 `http://localhost:11434/api/embed`。官方接口支持文本数组；设置 `truncate=false` 是为了让超长输入显式失败，再由切块逻辑处理，而非静默丢失后半段。[Ollama API 文档](https://docs.ollama.com/api/embed)

5. 查询侧使用任务指令，文档侧不加查询指令。建议初始查询模板：

```text
Instruct: Retrieve reference passages that answer the question, including relevant conditions and exceptions.
Query: {用户原始问题}
```

Qwen 官方示例区分查询指令与文档输入；0.6B 模型支持最高 1024 维表示。第一轮保留完整输出维度，启动时实测并登记，不依赖未经验证的维度缩减设置。[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)

6. 文档向量输入采用“文档标题 + 章节路径 + 原文子块”，保留原文为主。第一轮不使用生成问题替代正文，也不混合文件名向量。
7. 校验返回条数、维度一致性、有限数值和非零范数，再统一归一化；空文本不入索引。
8. 缓存键至少包含模型 digest、文档输入模板版本、完整输入文本哈希和实际维度；检索配置记录查询指令版本。
9. 初始批量 8、并发 1，记录冷启动与热请求耗时；按实际硬件调整，不预先承诺延迟。

涉及文件：新增 `knowledge/embeddings.py`、`configs/knowledge/rag.json`，调整依赖声明。嵌入调用应有独立模型用途标识，不混用聊天模型配置。

完成条件：真实 API 返回中文、英文及批量向量；相关/不相关片段的人工样例检查通过；服务停止、模型缺失、超长输入和响应异常都有明确失败结果。Mock 测试和真实模型测试分别记录。

## 5. 第 2 步：补齐来源元数据与结构切块

行动：

1. 新建文档清单 `configs/knowledge/documents.json`，记录 `document_id`、真实 `version`、路径、标题、来源类型、适用对象、量表版本、有效期及审核状态；未知字段保留未知。
2. `KnowledgeAgent` 从清单加载文档，移除统一写死的版本 `1`。
3. 扩展 `KnowledgeChunk`：增加章节路径、页码/原文区间、父块 ID、内容哈希和适用元数据。PDF 页码区分物理页与印刷页，不能混用。
4. Markdown 按标题树、段落、列表和表格切分；TXT 按段落处理；机器可读 PDF 复用已有 `TextParser` 的页码与 span 能力，通过适配进入知识库。
5. 父块以完整条款或小节为单位，子块按段落/句子组织。初始可尝试子块 400–800 个中文字符、父块 1200–2400 字符；这是长度启发式，不冒充 token 数，最终通过评测和实际输入限制修正。
6. 不跨章节盲目重叠；超长表格按行组拆分并重复表头，保留表注和单位关联。
7. 不可可靠抽取的 PDF、扫描件和复杂表格返回解析限制，转入第二轮处理，不将乱码或空文本当成功知识入库。

完成条件：抽检块能回到原文；版本与章节准确；包含条件例外的样例可由父块恢复；改变切块策略不会覆盖旧文档版本。

## 6. 第 3 步：构建词法与向量双索引

行动：

1. 新增索引存储适配，保存文档版本、父子块、词法表示、向量和索引 manifest。
2. 中文分词使用领域词表保留量表名、缩写；英文统一大小写，但编号、负号、单位和版本号不得被随意删除。
3. 向量只编码有效子块；父块用于上下文恢复，第一轮不重复进入候选竞争。
4. 按内容和处理版本增量计算，未变片段复用向量；模型 digest、文档编码模板或切块策略变化时建立新索引版本。
5. 提供命令入口：`knowledge_cli index`、`knowledge_cli inspect`、`knowledge_cli search`，实际命令参数在实现时固化。
6. 文档删除或失效后从活动搜索范围排除，历史证据仍可通过原始版本定位。

完成条件：重复构建结果稳定；重启后可查询；索引与模型维度不匹配时拒绝混用；新版切换不破坏旧引用；明确过滤条件应用于两路候选池，而非只在最终 Top K 后过滤。

## 7. 第 4 步：实现带适用条件的混合检索

行动：

1. 定义 `KnowledgeQuery`，输入问题及项目范围、文档集合、量表版本、时间等上下文。
2. 调用方明确提供的范围和版本作为硬过滤。模型推断的条件只作候选或提示，未经核验不转为硬过滤。必要适用信息未知时返回待确认状态。
3. BM25 和向量检索各取 Top 30，按 chunk ID 合并去重，使用 RRF 排序：`sum(1 / (60 + rank))`，rank 从 1 开始。
4. 返回融合 Top 10 作为初始候选，并记录 BM25 分数、余弦分数、各路排名和融合分数。
5. 将 `RetrievalHit.score` 调整为连续值或新增明确的分数字段，更新序列化、调用方和测试。不同分数都不是事实正确概率。
6. 硬条件过滤后无候选时，明确返回无匹配或适用信息不足，不静默放宽版本。服务故障与真实无匹配使用不同状态。
7. 词法单路可以作为显式降级模式，但输出必须标记模式和限制；不可把 Ollama 故障伪装成正常混合检索。
8. 在调参集校准拒绝弱相关候选的规则；RRF 排名本身不能判断库内一定存在答案，不直接套用其他模型的余弦阈值。

完成条件：中文整句、同义表达、精确编号和错误版本用例通过；保留现有精确命中能力；对比词法、向量和混合三组检索结果并登记退化问题。

## 8. 第 5 步：构造可供智能体使用的证据包

行动：

1. 新增 `knowledge/context.py`，根据命中子块找回父块，合并同一父块命中、去重并限制单文档占用。
2. 初始返回 3–6 个父块，预算服从实际下游模型。父块过长时选择命中段落与相邻条件，并显式标注截取，不能只留下结论丢掉例外。
3. 返回结构包含：问题、检索状态、索引版本、证据 ID、原文、文档版本、位置、命中说明、适用条件、冲突和限制。
4. 适用条件区分来自清单的已知字段与模型抽取的候选字段，后者必须关联原文区间。
5. 保留相互冲突的来源，不因一个分数略高就覆盖另一条；摘要与原文分字段，引用必须回到原文。

完成条件：原文与来源可核验；父块恢复不跨文档版本；冲突、例外、无答案均有明确表达；证据包能够在上下文预算内交给业务智能体。

## 9. 第 6 步：接入多智能体与规则候选流程

行动：

1. `KnowledgeAgent` 改为调用共享知识检索服务，避免每次执行扫描目录和建索引。
2. 业务任务显式传入问题与适用上下文；移除生产路径默认使用 `xx-v1 total scoring definition` 的行为，缺少问题返回输入不足。
3. 保留 `AgentResult` 主协议，按需要扩展 `output`，使结果可供现有汇总与报告链路使用。
4. 改造 `RuleCandidateBuilder`：规则候选需给出规则类型、条件、例外、原文引用和适用版本；第一轮对已有规则类型使用保守结构提取，未识别规则保留证据，不能仅凭“总分”就宣称完成语义提取。
5. 若引入模型提取，复用现有模型网关，执行 JSON 结构校验、原文引用校验和适用性检查；生成内容始终保持 candidate，不能自动改写可执行计分定义。
6. 检查并打通候选规则到现有注册服务的实际路径，增加“未激活不改变计分、激活后绑定规则版本”的测试，不能仅凭 limitation 文本认定机制已经实现。
7. 报告引用贯通到证据 ID 与文档版本；保持参考知识与患者观测的 kind 区分。
8. 若需要补充查询，先通过现有任务/质询机制发起有界检索，不另建无限 Agent 搜索循环。

完成条件：真实问题能由 KnowledgeAgent 返回有来源证据并被汇总消费；无匹配和服务失败不制造事实；规则候选不能直接改变计算；引用可回到对应版本原文。

至此完成第一轮基础检索闭环。

## 10. 第 7 步：依据评测添加效果增强

### 10.1 独立重排序

先对“已召回但排不到前面”的问题验证收益，再接入独立 reranker，取融合 Top 20–30 重排后选择最终证据。

`qwen3-embedding:0.6b` 只负责向量编码，不将余弦排序称为独立模型重排序。重排模型和运行方式尚未指定，第一轮不自动安装或承诺某个 Ollama 标签可用；第二轮先验证支持的调用接口与本机资源。只有固定评测集改善且延迟可接受时启用。

### 10.2 扩展复杂文档解析

以失败 PDF 和表格样例驱动 OCR、版面与表格结构解析的选择。参考 DeepDOC，先完成小样本原文对照，再接入同一来源协议。文档格式能力不能仅以“能打开文件”验收。

### 10.3 其他增强

- 关键词/问题生成：仅在表达覆盖不足时尝试，保留正文向量，派生表示必须能追溯原块并去重。
- RAPTOR：概括类问题证据分散时验证摘要层，摘要不能代替规则原文。
- GraphRAG：出现明确跨文档实体关系需求后验证。
- 多步检索：单次证据不充分且后续问题明确时引入，限制次数并复用现有预算机制。

每项增强单独做消融对比，不能一次全部启用后归因效果。

## 11. 验收指标与测试安排

以下为建议验收目标，属于方案目标，不是已取得的结果；先完成黄金证据核验和基线，再冻结参数与正式门槛。

| 项目 | 定义与建议目标 |
|---|---|
| Hit@10 | 可回答问题中前 10 个候选至少含一处正确黄金证据的比例，目标 ≥90%；同时报告样本数 |
| 多证据覆盖 | 对需多个原文区间的问题，单独统计必要证据覆盖率，不能由 Hit@10 代替 |
| MRR@10 | 第一处相关证据倒数排名均值，与现有基线及词法单路对比 |
| 版本/范围约束 | 已标注的硬过滤用例零越界 |
| 来源完整性 | 最终返回片段全部具有文档版本和可核验位置 |
| 无答案处理 | 测试用例不产生无证据规则或伪造引用，分别统计误答与漏答 |
| 条件完整性 | 条件与例外样例经逐条原文对照，不能只测字符串出现 |
| 规则边界 | 未激活候选不得改变评分；激活必须绑定明确版本 |
| 故障行为 | 模型缺失、服务失败、索引不兼容有可区分状态 |
| 性能 | 报告冷/热延迟、入库耗时、内存及实际文档/片段量，按本机实测确定预算 |

测试层次：

1. 单元测试：切块、来源定位、过滤、融合排序、向量响应校验和版本规则。
2. 集成测试：持久化索引、父块恢复、KnowledgeAgent 结果及报告引用。
3. 真实 Ollama 测试：独立标记，实际调用指定模型；依赖缺失时报告未执行，不用 Mock 结果代替。
4. 固定语料评测：保存每题候选、最终上下文、答案和失败归因；调参只用开发集。

建议新增 `tests/unit/test_knowledge_*.py`、`tests/integration/test_hybrid_knowledge.py`、`tests/acceptance/test_rag_evidence_flow.py`，扩展现有 `test_text_knowledge.py`。

## 12. 交付拆分与执行顺序

| 批次 | 覆盖步骤 | 可独立检查的交付 |
|---|---|---|
| A | 0–1 | 黄金问题集、原检索基线、真实 Ollama embedding 适配 |
| B | 2–3 | 文档清单、来源与父子切块、持久化双索引 |
| C | 4–5 | 范围过滤、混合检索、证据包、检索质量对比 |
| D | 6 | 多智能体消费、规则候选边界、报告来源闭环 |
| E | 7 | 根据失败样例选择重排序或复杂解析等增强 |

推荐严格按 A → B → C → D 推进。每批完成对应测试与样例后进入下一批；E 由实际问题驱动。
